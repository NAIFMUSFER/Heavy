# Picking and customer-approved substitutions

Status: the original substitution migration 20260910033534 and interfaces are deployed. Sixteen database groups passed, including consent, ownership, price, expiry and stock concurrency. The baseline browser journey verifies actual-weight preparation; explicit substitution consent has separate database/UI coverage. Real operator/device acceptance remains unverified. Configurable-weight migration 20260910101808 is applied after fourteen database groups and a 21-check browser journey passed; gateway promotion is pending; see WEIGHT-TOLERANCE.md and RELEASE-EVIDENCE.md.

An assigned picker (or admin) starts a queued order. Its original commercial snapshot remains unchanged. The picker records actual base-unit quantities, reports unavailable lines, or proposes a replacement from an active canonical offering. Proposals freeze the old line, new line, quantity, version identities, old and new order totals, sold coupon terms and exact price difference for fifteen minutes. Only one pending proposal is allowed per order, keeping the displayed total stable during review.

The customer explicitly accepts or rejects. Approval serializes against the order, delivery slot, sorted stock balances and lots. The transaction releases existing order allocations, computes requirements across all lines, reserves accepted FEFO lots that survive the delivery window and updates the current order snapshot. Any shortage rolls the complete transaction back. The proposal itself does not reserve additional stock; customer screens disclose that final availability is checked on approval. Already offered immutable product definitions remain valid if merchandising later deactivates them.

Rejection and expiry preserve original reservations and keep the unavailable line open. They never approve or remove an item implicitly. The picker must propose another alternative or explicitly record verified availability of the original item. Open issues and pending decisions block finalization. Restoring the original requires a reason and records the actor in the audit log. Physical verification is an operational responsibility; the database independently checks the usable reserved lot before consumption.

Actual quantities follow the immutable sold-version range. Lower weight scales the price proportionally; original coupon terms continue to apply. Configured extra weight is included in the quoted price and must reserve actual FEFO stock transactionally; see WEIGHT-TOLERANCE.md. Weighted basket components retain their fixed composition. Finalization consumes the current approved allocations once and records lot cost against the order. Original order snapshots are retained.

API routes use persisted `Idempotency-Key` requests through `jana_picking_write`: actual quantities, proposals, unavailable/restored lines, completion and customer decisions. Reuse with a changed request is rejected. Native customer decisions preserve retry keys in SecureStore across application restarts. Internal reallocation and base finalization helpers cannot be invoked by browser, authenticated Supabase or service-role clients directly.

The existing minute scheduler expires quotes and substitution proposals. Expiration notifies the customer and leaves unresolved picking work visible. The migration refuses to proceed with pending legacy proposals, which need operational review first. Existing terminal proposal history is preserved.
