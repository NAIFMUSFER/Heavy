# JANA architecture and business truth

The established canonical deployment is `NAIFMUSFER/Heavy` on `jana-live`, Render service `srv-dagnferl550s73cbivhg`, and dedicated Supabase project `jjdsajiwoqanefmnikls`. The unrelated default repository branch and all non-JANA infrastructure are out of scope. Source changes are reviewed on `jana-integrity`; promote the exact tested tree to the production branch.

Web and Expo clients call the Node gateway. The gateway assembles the existing browser bundles, serves an explicit public-file allowlist and proxies only fixed JANA Edge destinations. It has no database service key. Gateway cookies are HttpOnly/Secure/SameSite=Strict; CSRF is validated on cookie writes. Mobile uses custom opaque Bearer sessions in SecureStore. PostgreSQL stores session-token hashes and validates active users and server-side roles. This application currently uses its own users/sessions model, not Supabase Auth JWTs. Existing Edge functions intentionally retain custom authentication with platform JWT verification disabled; changing this requires an authentication migration, not a configuration toggle.

`jana-api` handles catalog, authentication, profiles, checkout and the customer/operations workflows. `jana-critical` handles the existing critical checkout routes. `jana-ops-extra` handles catalog, inventory, delivery configuration and financial operations. Their shared HTTP modules enforce Origin, request-size and CSRF controls. They resolve transactional RPCs using Edge-only platform credentials. Application tables have RLS and no direct anonymous/authenticated access. Public-read RPCs also flow through the trusted gateway.

PostgreSQL enforces inventory and lot nonnegative balances, reservation bounds, slot capacity, one order per quote, persisted write idempotency, immutable commercial definitions and append-only financial/stock/audit records. Product family, version and sellable offering are distinct. Existing `offerings.family_id` identifies a stable sellable lineage used by favorites/lists; canonical product family and version identities are separately included in current quotes and new offerings. Do not reinterpret the legacy field during client development.

Quotes reserve stock, lot allocations, delivery capacity and any coupon usage in one transaction. Confirmation copies commercial terms to an order and preserves its original snapshot. Scheduled expiry releases unused quote resources. Picking consumes current approved allocations and writes inventory cost movements. Substitution approval can replace allocations and current price only with explicit customer consent; its original snapshot remains intact. Monetary values use integer halalas. Inventory uses canonical gram/piece base quantities. Operational timestamps are epoch milliseconds; reporting and customer schedules use Asia/Riyadh.

Delivery proof and cash collection are separate events. Collected cash creates courier liability. Partial deposits and refunds paid from courier cash reduce that liability; company-funded refunds do not. Deferred constraints reconcile order financial fields against the cash and refund ledgers at commit. Profit is an estimate; unknown cost remains unknown. See financial and picking documents for details.

Current expansion boundaries: delivery polygons and slots support multiple Saudi cities without textual coverage matching. Inventory is currently a single shared pool; multi-warehouse stock segregation, location-specific FEFO and independent fulfillment routing remain required before operating distinct city warehouses. Address city text alone never grants coverage. A future warehouse dimension must be introduced transactionally into lots, balances, allocations and reporting before routing orders across hubs.

Notification records are currently in-app. The Resend email adapter and durable worker boundaries are implemented and regression tested; approved domain/destinations, configuration and a dedicated worker are required before activation. SMS/WhatsApp/push/online payment implementations remain pending. PostHog capture requires dedicated JANA project variables; unavailable feature flags fail closed. No shared analytics project is approved. Web/mobile product images render validated HTTPS metadata with an image-failure fallback; uploading/removing images through an inspected storage provider remains pending.

Local cart persistence and monetary/date input helpers are shared across web and native, with executable source-parity checks. Cart writes are serialized; failed persistence does not publish an unsaved quantity. Damaged stored records require retry or an explicit device-cart reset. Account restoration and catalog loading remain separate from cart storage; successful reads do not write local preferences. See REVIEW-2026-09-11.md for scope and limitations.
