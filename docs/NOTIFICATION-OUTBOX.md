# Durable optional notification delivery

Status: implemented locally; PostgreSQL/browser gates and deployment are pending. All external channels start disabled. No existing in-app event is backfilled, no destination is inferred from an account email/phone, and no external message is sent by installation. Current in-app commerce notifications remain transactional.

After a canonical notification is inserted, an outbox trigger creates at most one job per notification/channel only when the channel is explicitly enabled, the provider configured, and a separate verified destination with recorded consent is active for an active customer. Destination verification/consent must come from an owner-approved provider workflow; these records have no browser write API. Neither enabling channels nor asserting recipient ownership is performed by this release.

The job snapshots the exact recipient, title, body, provider, approved sender scope, retry window and maximum attempts. Those terms cannot be edited. Service-only claim/finish RPCs use row locks, SKIP LOCKED, a two-minute lease, random lease fencing and at most eight attempts. Each claim, expiration and result is retained in immutable attempt evidence. A lost worker or response is an unknown outcome. Retries keep the same provider idempotency key and use exponential delay from 30 seconds to one hour, within an immutable maximum 23-hour window. Stale acknowledgements are rejected; an identical completed acknowledgement returns its persisted result.

A provider ID records submission, not recipient delivery. Unknown final outcomes and expired attempted jobs require reconciliation. A later known rejection cannot erase an earlier unknown submission. Permanent known-unsent failures become visible dead letters. Revoked/changed destinations block new attempts; cancellation after a previous attempt requires reconciliation. Disabling a channel blocks new claims/enqueues but cannot retract a request already in flight.

`server/providers/notification-repository.mjs` binds InAppProvider to `jana_notification_insert_once`, including same-event content-conflict checks. It also binds worker claims/acknowledgements to the dedicated JANA database. `server/notification-worker.mjs` currently dispatches email through the existing Resend adapter. Other channels retain explicit configuration-required adapters.

Worker command: `node scripts/notification-worker.mjs`; one supervised iteration: `node scripts/notification-worker.mjs --once`. It fails closed unless `JANA_NOTIFICATION_WORKER_ENABLED=true` and `JANA_EMAIL_ENABLED=true`, the pinned JANA Supabase URL and dedicated server-side `JANA_SUPABASE_SERVICE_ROLE_KEY` exist, and Resend configuration is valid. Required provider/domain variables remain documented in PROVIDERS.md. Requests use fixed HTTPS hosts, reject redirects, have timeouts and keep private responses out of logs. No worker service is provisioned or running by this release; deploying/enabling a sending worker requires approved account/domain/recipient configuration.

`GET /api/ops/notification-jobs` gives admin/support channel states, exact state counts and the last 50 redacted jobs. The monitoring page exposes no recipient, message body, user contact, lease or credentials. It has no send/retry/activation controls. Reconciliation is an operator check against actual provider evidence; no blind resend or fabricated delivered state is available. A signed delivery/bounce webhook and a destination-verification provider flow remain integration requirements.

Configuration changes and destination registration must be performed through a reviewed owner-authorized trusted transaction with an audit event. Do not set verified_at/consent_at merely because an address is present on an account. Do not add production fixture recipients or enable a channel to make a health check pass. Outbox health is independent from commerce readiness while channels are disabled.

Sender scope is SHA-256 of the Resend domain ID, domain name and sender address array (the exported resendScope function). The database channel setting must contain the reviewed matching scope before activation. Claimed jobs bind to that immutable scope, preventing a later worker configured with a different sending domain/account from silently resubmitting an uncertain job. Key rotation within the same verified sender scope is supported. Changing sender scope requires reconciliation of older pending jobs.
