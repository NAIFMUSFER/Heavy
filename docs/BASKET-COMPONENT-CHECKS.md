# Fixed basket component measurement

Release numbers below record this feature's original validation. Current deployed versions and subsequent gates are maintained in [RELEASE-EVIDENCE.md](RELEASE-EVIDENCE.md).

An assigned picker or administrator records the measured total of each component in a multi-component sold line. Quantities scale by the number of baskets and retain the canonical unit of each stock item: grams and pieces are never summed together. Initial inputs are blank; the operator explicitly attests to physical measurement. Zero records an absent component. All members of the sold component set must be present exactly once, with bounded integer amounts.

The record is operational evidence, not a stock adjustment or a new price agreement. Saving a shortage or excess leaves the customer-approved price, coupon terms, original order snapshot, reservations, lot balances and cost/cash ledgers unchanged. The normal finishing transaction remains blocked until each measured amount matches the sold component quantity. Staff can complete the original quantity, use a whole-line substitution, or propose an exact component replacement under the bounded rule below. A discount for an omitted component and weight tolerances or variance pricing for fixed baskets remain separate commercial-policy work; the application does not infer them.

After a recorded shortage, an assigned picker or administrator may propose one active replacement stock item that is not already another component in the same line. It must use the same base unit and exact sold base quantity. The fixed basket line, coupon, subtotal and total remain unchanged. Proposal and rejection/expiry do not move reservations. Explicit customer approval atomically releases and rebuilds the order reservation with the replacement, records distinct immutable events, and removes the old component measurement. Finishing stays blocked until the picker measures every component in the newly approved composition. If replacement stock is no longer available at approval, the transaction rolls back without changing the customer's order or inventory.

PostgreSQL enforces the rule for both finalization endpoints, the persistent dispatcher and legacy `ready` transitions. It preserves the existing unavailable-item and pending-consent checks. Already prepared orders are not rewritten; existing successful persistent retries retain their saved responses. Single-component products retain their current versioned weight and proportional-price rules.

`POST /api/ops/orders/:id/components` takes `line_id`, the `revision` returned by the picking detail, and `items: [{stock_id, actual_base}]`. The path supplies the authoritative order ID. The database authenticates the current assigned picker/admin, validates the exact typed body, locks the idempotency key then the order, rejects stale revisions and appends a measurement event and audit record. Same-key retries return the original response; changed payloads conflict. Order updates and unavailable/restored transitions advance the order's picking revision, so old forms cannot overwrite new evidence or a customer-approved replacement. A replacement carries no measurement from the original line.

The revision triggers and component predicate have no public or service-role execute grant; the authenticated RPC is available only to the server role. The custom JANA session and gateway CSRF boundaries remain in force. See [Supabase function privileges](https://supabase.com/docs/guides/database/functions#function-privileges) for the platform permission model.

Disposable PostgreSQL tests exercise strict types, complete component sets, zero/short/excess quantities, actual consumption and costs, duplicate retries, competing measurements, finishing races, assignment changes, whole-line replacements and component proposal/approval/rejection/expiry. Component tests verify no pre-consent inventory change, concurrent decision idempotency, same-unit/exact-quantity rules, atomic reallocation and required fresh measurement. The browser journey uses the real catalog editor, quote/order transaction, picking form and database. Production test inventory/orders are not created.

Release state and actual test results are recorded in RELEASE-EVIDENCE.md. The measurement interface serves warehouse web users; exact component replacement also includes explicit customer consent on web and native. Native device acceptance and commercial launch approval remain outstanding.
