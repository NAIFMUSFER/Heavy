# Fixed basket component measurement

An assigned picker or administrator records the measured total of each component in a multi-component sold line. Quantities scale by the number of baskets and retain the canonical unit of each stock item: grams and pieces are never summed together. Initial inputs are blank; the operator explicitly attests to physical measurement. Zero records an absent component. All members of the sold component set must be present exactly once, with bounded integer amounts.

The record is operational evidence, not a stock adjustment or a new price agreement. Saving a shortage or excess leaves the customer-approved price, coupon terms, original order snapshot, reservations, lot balances and cost/cash ledgers unchanged. The normal finishing transaction remains blocked until each measured amount matches the sold component quantity. Staff can complete the original quantity or use the existing explicit customer-approved whole-line substitution workflow. Component-level substitution, a discount for a missing basket component, and weight tolerances for fixed baskets remain separate commercial-policy work; this change does not choose those policies.

PostgreSQL enforces the rule for both finalization endpoints, the persistent dispatcher and legacy `ready` transitions. It preserves the existing unavailable-item and pending-consent checks. Already prepared legacy orders retain their existing idempotent completion behavior. Single-component products retain their current versioned weight and proportional-price rules.

`POST /api/ops/orders/:id/components` takes `line_id`, the `revision` returned by the picking detail, and `items: [{stock_id, actual_base}]`. The path supplies the authoritative order ID. The database authenticates the current assigned picker/admin, validates the exact typed body, locks the idempotency key then the order, rejects stale revisions and appends a measurement event and audit record. Same-key retries return the original response; changed payloads conflict. Order updates and unavailable/restored transitions advance the order's picking revision, so old forms cannot overwrite new evidence or a customer-approved replacement. A replacement carries no measurement from the original line.

The revision triggers and component predicate have no public or service-role execute grant; the authenticated RPC is available only to the server role. The custom JANA session and gateway CSRF boundaries remain in force. See [Supabase function privileges](https://supabase.com/docs/guides/database/functions#function-privileges) for the platform permission model.

Disposable PostgreSQL tests exercise strict types, complete component sets, zero/short/excess quantities, actual consumption and costs, duplicate retries, competing measurements, finishing races, assignment changes and customer-approved replacements. The browser journey uses the real catalog editor, quote/order transaction, picking form and database to record and correct a shortage. Production test inventory/orders are not created.

Release state and actual test results are recorded in RELEASE-EVIDENCE.md. This source change concerns the warehouse web interface and backend; native device acceptance and commercial launch approval remain outstanding.
