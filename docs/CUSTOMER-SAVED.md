# Customer lists, profile and recurring reminders

Shopping lists reference a stable sellable lineage (including size), not a browser price or mutable product name. PostgreSQL validates quantities, combines duplicate lines and resolves current catalog name, version, price and availability for display. Missing or inactive offerings retain historical labels and expose an unknown price. Empty lists are supported; each customer may keep up to 50 lists with 60 distinct lines and quantity 1–20 per line.

List revisions detect conflicting edits across devices. Rename, item edits and deletion use an expected revision; stale writes return a conflict. Creation and mutations have persisted idempotency. Adding a complete list to a cart checks a fresh catalog and all merged quantities before changing the existing cart. If any requested quantity is unavailable, the UI asks for correction; it does not claim a partial addition was complete. A cart availability check is not a reservation; the quote transaction remains authoritative.

Recurring plans initially produce in-app reminders only. They never create orders, reserve stock or slots, charge a payment method or send external messages. Customers choose an owned address, a future reminder time, items and weekly/fortnightly/monthly cadence. Monthly reminders use the chosen Saudi calendar day, clamp to the last day in a short month, and recover the original day in a later month. Legacy custom-day intervals remain explicit. A late worker sends one reminder and advances past missed occurrences, rather than sending a backlog. Pause/cancel stop reminders. Resuming an expired paused schedule requires a new future time. Cancellation is terminal; a new definition is required to restart it.

The worker runs each minute under `jana-recurring-reminders`. User then plan row locks, rechecked due state, skipped locked plans and unique notification keys prevent duplicate reminders and coordinate profile/deletion operations. Tests change the cadence to two seconds only in disposable localhost PostgreSQL and verify actual pg_cron execution.

Profiles allow name, optional phone and explicit Arabic/marketing preference settings. Role and phone-verification state cannot be selected by the customer. Changing a phone clears its verification flag; no SMS verification is fabricated. Login email remains required by the current authentication model. Optional-email/phone-login onboarding still needs a separate implementation; this profile endpoint does not claim to provide it.

The web and mobile interfaces support saved-list editing, adding a list to cart, recurring plan review/pause/cancel and profile preferences. Mobile creation retries persist keys in SecureStore. Mobile also exposes category/search, product detail, favorites and Arabic order labels. Some mobile catalog selectors currently load the first 100 offerings; larger catalog pagination and device acceptance remain outstanding.

API routes: `GET/POST /api/shopping-lists`, `PATCH/DELETE /api/shopping-lists/:id`, `GET/POST /api/recurring`, `PATCH /api/recurring/:id`, and `GET/PATCH /api/profile`. Mutations require `Idempotency-Key`. Edits/deletions require `revision`; new reminder timestamps are UTC epoch milliseconds, displayed and entered in Saudi time.

Calendar implementation follows PostgreSQL's [time-zone and interval semantics](https://www.postgresql.org/docs/17/functions-datetime.html); workers use [row locking](https://www.postgresql.org/docs/17/sql-select.html). These mechanisms are verified against the real restored PostgreSQL schema in CI, not a simulated inventory backend.
